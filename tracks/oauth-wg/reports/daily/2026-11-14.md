### Agent Passport author spells out -01 rules for cumulative limits, RAR grants and per-constraint attenuation of delegation receipts

`mail` · `new-proposal` · first seen 2026-11-13 · [New draft: Agent Passports and Delegation Receipts (draft-le-agent-passport-00) (2 new messages)](https://mailarchive.ietf.org/arch/msg/oauth/J309gZABiOnSsvebrwYUWTi1Aow/)

In reply to Kieran Sweeney, Ben Le says -01 will require a receipt with a cumulative limit to name exactly one relying party, which alone counts for the receipt and all its children. A limit without a single named party will be invalid. Sharing a total across relying parties is out of scope, and whether another party in the call path could keep the total is left open. He will define an RFC 9396 authorization_details type for grants so an authorization server that supports RAR can issue root receipts directly, while Token Exchange remains the path for an agent that obtains a receipt using its passport as actor token. He also gives a per-constraint subsumption table (host, port, methods, paths, tools, max_body_bytes, max_calls, max_spend, exp, aud). A child attenuates its parent only if every rule holds, unknown members are rejected, and anything not comparable is rejected. -01 has only a fixed limit of 8 receipts per chain and no depth claim. He plans to join Niki's comparison side meeting on 16 November and hold his own on 17 November, ahead of IETF 127.

**Use cases**

- An authorization server that already supports RAR could issue root delegation receipts for agents using a new authorization_details type.
- A relying party enforcing a cumulative spend or call cap on an agent chain must be the one named counter in the receipt.
- Implementers of several agent delegation drafts can use the per-constraint attenuation table as a basis for shared test vectors.

### AAT-02 thread: compare leaves that carry an action binding apart from leaves that cite a separate approval proof, and record shared replay state

`mail` · `discussion` · first seen 2026-11-12 · [AAT -02 announcement (2 new messages)](https://mailarchive.ietf.org/arch/msg/oauth/WixDZ1_uCFhHcyVW7y0ao-hXWpQ/)

Mohamad Yossif argues that a chain leaf need not express the binding to one exact request itself. It can carry the digest of, or cite by jti, a separate proof. He describes draft-yossif-psea-03 as a proof signed by the approver's enrolled device over the SHA-256 of the request in RFC 8785 form, which a verifier refuses on replay. He suggests the comparison list "not expressible in the token" and "expressible by reference" as two entries. Iman agrees, would keep the action identifier, approval jti and proof reference distinct, and notes that conformance case DR-C7 only checks a second presentation to the same verifier. Iman proposes a new test presenting one proof through two leaves at two enforcement points and checking that at most one finalization succeeds, which separate local replay caches would not show. The thread contains no draft text change.

**Use cases**

- Authors of an agent authorization token who must decide whether per-request approval is carried in the token or referenced from an external proof.
- Deployers running several enforcement points in one verification domain who must decide whether replay state has to be shared across them.
