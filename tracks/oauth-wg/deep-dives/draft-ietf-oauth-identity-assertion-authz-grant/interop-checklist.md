# Interop Checklist

- [ ] The IdP rejects a Token Exchange request with no client authentication using `invalid_client` (Section 4.3.3).
- [ ] The IdP rejects a request with more than one `audience` value using `invalid_request`, and rejects an `audience` it has no trust relationship with using `invalid_target` (Section 4.3.3).
- [ ] The IdP returns `invalid_request`, not `invalid_grant`, when the subject token is expired, malformed, has the wrong audience, or is an expired or revoked Refresh Token (Section 4.3.4.3).
- [ ] The IdP returns `access_denied`, not `invalid_target`, when the subject token is valid but the Client or End-User is not authorized for the target (Section 4.3.4.3).
- [ ] The IdP rejects an access token, an ID-JAG, a client assertion, or a SAML assertion issued for another purpose when presented as `subject_token`, and rejects a JWT whose `typ` identifies another token type (Section 4.3.3).
- [ ] For an Identity Assertion, the subject token audience (ID Token `aud` or SAML Audience) equals the `client_id` used for client authentication, and the SAML Audience is mapped to a Client ID (Sections 4.3.3 and 4.5).
- [ ] Granted `resource` values are copied exactly as the Client sent them, compared with Simple String Comparison, and `invalid_target` is returned if none are granted or a required `resource` is absent (Section 4.3.3).
- [ ] The Client puts the `resource` value from validated Protected Resource Metadata into the request unchanged, and has checked the RFC 8414 `issuer` and RFC 9728 `resource` values before sending anything (Sections 4.3, 9.5 and 9.6).
- [ ] The Token Exchange response has `issued_token_type` `urn:ietf:params:oauth:token-type:id-jag`, `token_type` `N_A`, the ID-JAG in `access_token`, and `scope` whenever it differs from the request (Section 4.3.4).
- [ ] The ID-JAG header `typ` is `oauth-id-jag+jwt`, the required claims `iss`, `sub`, `aud`, `client_id`, `jti`, `exp` and `iat` are present, RS256 is accepted, and an `id_jag_signing_alg_values_supported` list, if published, includes RS256 (Sections 3, 3.1 and 7.1).
- [ ] The Resource Authorization Server accepts `aud` as a string or a one-element array equal to its issuer, and rejects any other array or value with `invalid_grant` (Section 4.4.1).
- [ ] The Resource Authorization Server rejects with `invalid_grant` when the `client_id` claim does not identify the authenticated client, and when no client authenticates it requires a valid `cnf` proof (Section 4.4.1).
- [ ] The Resource Authorization Server rejects a request with neither client authentication nor a sender-constrained ID-JAG using `invalid_client` (Section 4.4).
- [ ] For a multi-tenant issuer the ID-JAG carries `tenant`, and the Resource Authorization Server rejects it with `invalid_grant` when the tenant is missing, untrusted for the pair of `iss` and `tenant`, or the recipient tenant is ambiguous (claim in Section 3; Sections 6.1 and 4.4.1).
- [ ] The Resource Authorization Server keeps `aud_tenant`, `aud_sub` and `client_id` consistent with its tenant model, and the same End-User always gets the same `sub` for a given Resource Authorization Server and `aud_tenant` regardless of Client (claim in Section 3; Sections 5.2, 6.2 and 6.3).
- [ ] Every identifier in the `resource` claim is governed by the Resource Authorization Server for the right tenant, or the request fails with `invalid_grant`, and the issued access token is restricted to those resources (Section 4.4.1).
- [ ] An ID-JAG with an unsupported `cnf` confirmation method, a `cnf` with no proof, or a thumbprint mismatch fails with `invalid_grant` for both `jkt` and `x5t#S256` (Sections 9.11, 9.11.1.2 and 9.11.2.2).
- [ ] A DPoP-bound ID-JAG is redeemed with grant type `urn:ietf:params:oauth:grant-type:jwt-dpop`, and the Client checks that the returned ID-JAG has the `cnf` it asked for (Sections 4.4 and 9.11.1.1).
- [ ] When both a DPoP proof and a client certificate are presented on the Token Exchange request, the IdP binds the ID-JAG to only one mechanism (Section 9.11).
- [ ] SAML NameID `sub_id` never uses a transient NameID, includes `sp_name_qualifier` when the NameID is scoped to a Service Provider, is compared on every member the Resource Authorization Server uses, and the ID-JAG issuer is tied to the SAML issuer through local configuration rather than through `sub_id.issuer` (Sections 3.2.2 and 9.8).
- [ ] A Resource Authorization Server that requires a SAML NameID `sub_id` rejects an ID-JAG with no `sub_id`, a malformed `sub_id`, an unsupported format, or an unauthorized issuer using `invalid_grant` (Section 3.2.2).
- [ ] Client retry logic distinguishes `invalid_request` at the IdP from `invalid_grant` at the Resource Authorization Server. A new ID-JAG may resolve `invalid_grant` but will not resolve `access_denied`, so a client should not keep requesting new ID-JAGs after `access_denied` (Sections 4.3.4.3 and 4.4.3).
- [ ] A Resource Authorization Server that advertises `urn:ietf:params:oauth:grant-profile:id-jag` also lists `urn:ietf:params:oauth:grant-type:jwt-bearer` in `grant_types_supported`, and a client that advertises it lists both the token-exchange and jwt-bearer grant types (Sections 7.2 and 8).
- [ ] Error descriptions at both servers do not reveal whether the End-User holds a license or entitlement (Section 10).
- [ ] The IdP does not issue access tokens in response to an ID-JAG it issued itself unless explicitly configured, and the same ID-JAG is never used as a grant for a different downstream Resource Authorization Server (Section 9.4).
