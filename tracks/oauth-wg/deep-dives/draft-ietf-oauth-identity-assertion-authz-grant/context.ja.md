# 背景

## きっかけ

パイプラインは、トリアージ後の OAuth WG の候補の筆頭として、revision -06 の draft-ietf-oauth-identity-assertion-authz-grant (Datatracker 上の状態: Active, I-D Exists, WG Document) を選んだ。トリアージのメモは -06 に広範な規範的変更があるとしているが、-04、-05、-06 の本文を比較すると、その大半は -05 で入ったものであり、-06 で変わったのは subject token のエラーコードである。著者による OAuth メーリングリストでのアナウンスも、これらの変更は主に実装からのフィードバックに基づく明確化であり、フローと全体の設計は変わっていないと述べている。

## これが重要な理由

ID-JAG は、非公式には Cross-App Access (XAA) と呼ばれ、アプリケーション間の API アクセスを仲介する判断を、両アプリケーションがすでに SSO に使っている IdP に移す。ドラフト自身のユースケースには、エンタープライズの SaaS 連携、カスタマーアイデンティティのプラットフォーム、メールおよびカレンダーのクライアント、外部ツールを呼び出す AI エージェントが含まれる (Appendix A)。グラントはユーザーへの確認なしに引き換えられるため、チェーン全体の安全性は、正しいクライアント認証、トークンの種別判定、audience とリソースの確認、テナントの扱い、そして任意で送信者制約に依存する。これらの規則のいくつかは -05 と -06 で厳しくなったため、独立した実装ほど食い違いが生じやすい。著者らによれば、IdP、認可サーバー、クライアント、ライブラリにわたって現在すでに多数の実装がある。

## 未解決の論点

- 期限切れの入力に対して IdP では `invalid_request`、Resource Authorization Server では `invalid_grant` が返ることを踏まえ、クライアントは再試行ロジックで 2 つのエラーのエンドポイントをどう区別すべきか (Section 4.3.4.3、4.4.3)。
- ワーキンググループのリポジトリにある未解決の issue (たとえば README.md でリンクしている #141、#142、#145、#129、#114) のうち、どれを著者が IETF 127 に持ち込むのか。アナウンスには書かれていない。
- 本ドラフトが 2 つの Work in Progress のドラフト (Identity Chaining と DPoP JWT グラント) に依存していることにより、それらの進展に伴ってここにも変更が生じるかどうか。
