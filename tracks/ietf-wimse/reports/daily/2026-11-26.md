### draft-le-agent-passport-01 is posted. Revocation now fails closed and cumulative limits are counted by one RP

`mail` · `substantive` · first seen 2026-11-26 · [draft-le-agent-passport-01 posted](https://mailarchive.ietf.org/arch/msg/wimse/LcmaHpAV4z6s0htiS4XbWYKaQFU/)

The announcement lists the main changes in -01. Revocation fails closed when no fresh status is available, with a stated bound on how long a withdrawn principal can still be relied on. A cumulative limit is counted by exactly one RP, and grants can be requested as a RAR authorization_details type. Transport and intermediary rules are added, with @authority always covered. A root receipt can record how the person approved the delegation, including a WebAuthn assertion. The draft also adds a table mapping it to cross-organisation delegation requirements and a comparison with other attenuation formats. A public relying-party verifier under Apache-2.0 covers the IETF 127 hackathon scenarios.

**Use cases**

- An RP that accepts agent passports must decide what to do when the status list cannot be fetched.
- A deployer wants to request agent grants through RAR authorization_details.

### A new draft makes each hop of an agent delegation chain signed by the previous agent's key. The le-agent-passport author says it should be the default

`mail` · `new-proposal` · first seen 2026-11-26 · [New draft: Delegator-Bound Delegation Chains for AI Agents:](https://mailarchive.ietf.org/arch/msg/wimse/ixBxKlbk-bJEce-E5Lja4BM3MUQ/)

Suhas Nandakumar and Cullen posted draft-nandakumar-wimse-delegator-bound-chains, which extends the Delegation Tokens of draft-asor-wimse-agent-delegation-chain. Each token is signed with the key the previous token names in cnf, and its iss is the previous token's client_id. Only the root rests on a trust anchor. A del_bind claim in the root enables this for the whole chain, and later hops cannot turn it off. The draft also adds a per-chain pseudonym for the person, cycle detection, audience attenuation and context binding. Ben Le replies that draft-le-agent-passport makes delegator binding the only mode, with each child receipt signed by the holder key of the passport whose thumbprint is in cnf.jkt. He leans towards a default in the Delegation Tokens draft rather than an extension, and says the same key signs the next receipt and the request.

```mermaid
flowchart LR
R[Root token signed by trust anchor] -->|cnf names key A| H1[Hop 1 signed by key A]
H1 -->|cnf names key B| H2[Hop 2 signed by key B]
H2 --> V[Verifier checks the chain offline]
```

**Use cases**

- Agents in different organisations delegate directly to each other with no server to vouch for each step.
- A verifier checks offline that each hop was actually granted by the agent before it.

### Jiahui Miao proposes separate, test-first rejection criteria for workload-instance binding, drawn from the WIMSE HTTP signature test vectors

`mail` · `discussion` · first seen 2026-11-26 · [Workload-instance binding needs rejection criteria, not just identity formats](https://mailarchive.ietf.org/arch/msg/wimse/qYxPk16KTdlQ5KyD4r3-fBxL8Ms/)

Citing the R9(f) gap in draft-cea-list-vaultys-oauth-agent-deleg-reqs-gaps-00, the author notes that DPoP and mTLS prove key possession but not that the workload instance the authority was delegated to is using the key. From the 29 vectors in draft-miao-wimse-http-signature-test-vectors-00, 23 of them negative, three criteria are proposed. Instance mismatch is a rejection class distinct from signature invalidity. The binding check runs against the presented instance identity, not the key that produced the proof. A proof that verifies but names the wrong instance is a negative case. The author says these are criteria and test material, not a binding specification, and asks whether the list wants this as a separable work item.

**Use cases**

- A WIMSE HTTP signature verifier needs negative tests for a valid signature presented by the wrong workload instance.
- Authors of agent delegation specifications need rejection criteria for instance binding.

### The -02 of the post-quantum agent identity draft tightens wording on the binding gap and requirements, mostly from reviewer feedback

### A new individual draft proposes per-tool-call authorization for AI agents, using the intersection of agent, sponsor and session permissions

`mail` · `new-proposal` · first seen 2026-11-25 · [New draft: draft-pandey-agent-identity-00 — Session-Scoped Authorization for AI Agents](https://mailarchive.ietf.org/arch/msg/wimse/iB-0pc72P_IaEPpeRgpmBYrHfhA/)

Karmendra Pandey announced draft-pandey-agent-identity-00. Each agent is its own principal bound to a human sponsor through a delegation chain. Authorization is evaluated at every tool call, with effective permissions as the intersection of the agent's, the sponsor's and the session scope. Unevaluable actions are denied, irreversible action classes need sponsor approval, and each call yields a tamper-evident audit receipt. The draft defines no new protocol and requests no IANA actions. Review is requested on the intersection rule, fail-closed behaviour and reuse of the receipt.

```mermaid
flowchart LR
  A[Agent permissions] --> I[Intersection]
  S[Sponsor permissions] --> I
  C[Session scope] --> I
  I --> D{Tool call allowed?}
  D -->|yes| R[Execute and issue audit receipt]
  D -->|no or cannot evaluate| X[Deny]
```

**Use cases**

- An MCP or tool gateway that must decide per call what an agent acting for a user may do.
- Producing audit receipts for each agent action to support later dispute or review.

**Related in other tracks**

- `oauth-wg` / `draft-ietf-oauth-transaction-tokens`: Both carry per-call context for downstream authorization decisions, though the mail does not reference it.

### Test vectors say a bare key set must never be reported as binding the root key to a party; only a validated certification path can

`mail` · `discussion` · first seen 2026-11-25 · [Trust-anchor provenance (draft-asor-wimse-agent-delegation-chain-02, Section 6.4)](https://mailarchive.ietf.org/arch/msg/wimse/iGTW6JAv6Nt81CwR7734xbaR3p8/)

Sankalp Gilda describes a third test vector, R25, in the agent-evidence-vectors repository. It is R13 with the root element changed to a key set holding one P-256 key and no certificate. A verifier must report the key's RFC 7638 thumbprint and algorithm family, and must report the key-to-party binding as not established. R13 (Ed25519 key set) now reports the same. A verifier that reports the binding as established disagrees with the vectors, and one that omits the binding is read as reporting none, not as a pass. The same rule goes into proposed text for the next revision of draft-gilda-audit-agent-audit-record. The remaining case is a root element with a certification path naming the party. There the verifier validates the path to a trust anchor it already holds, and reports the party and each certificate's signature algorithm, as Section 6.4 asks. An expired-certificate vector will accompany it. Holding the anchor is configuration and no topology is mandated. Gilda also announces vectors R3, R4 and R19 for receipt-time checks (PQ-R7(c)), in v0.38.0: R3 and R4 are malformed, R19 is the well-formed boundary case.

```mermaid
flowchart TD
  A[Root element] --> B{Type}
  B -->|Key set, no certificate| C[Report thumbprint and algorithm family]
  C --> D[Binding to party: not established]
  B -->|Certification path| E[Validate path to held trust anchor]
  E --> F[Report party and per-certificate algorithms]
  E -->|Expired or invalid| G[Reject, do not read party off the path]
```

**Use cases**

- A verifier implementer checking its handling of audit-record root elements against the published vectors before claiming conformance.
- A relying party that receives delegation-chain evidence with a bare key set and must decide whether it may treat the key as belonging to a named party.

### The author of draft-hulea-wimse-agent-mandate asks whether WIMSE should cover proof that a delegator was entitled to delegate

`mail` · `discussion` · first seen 2026-11-25 · [Evidence that the delegator could delegate: interest in WIMSE?](https://mailarchive.ietf.org/arch/msg/wimse/zeMYPRXMTA5bRnWssKMeJj7XJNA/)

Claudiu Hulea notes that delegation chain drafts show no hop exceeds its parent, and draft-nandakumar-wimse-delegator-bound-chains adds that each hop was granted by the parent's holder. The root still rests on a trust anchor, which shows who signed it, not that the delegator could grant its contents. draft-hulea-wimse-agent-mandate-01 proposes an Authority Assertion: a statement signed by a source the relying party trusts (for example a company register or signatory policy) of what the delegator may grant. The root mandate references it by digest and the Validator checks the root stays within it. He asks whether this is a WIMSE gap, possibly for the AIMS gaps section, or belongs elsewhere, and requests review of Section 9.4 before -02.

```mermaid
flowchart LR
  A[Authority source: register or signatory policy] -->|signs Authority Assertion| B[Assertion]
  C[Delegator] -->|root mandate with digest of assertion| D[Chain]
  B --> E[Validator]
  D --> E
  E -->|root within assertion?| F[Accept or reject]
```

**Use cases**

- A bank in another domain accepting a treasury agent's payment mandate without holding the company's onboarding file.
- A relying party that wants to verify a root delegation stays within what the issuing officer could commit.
