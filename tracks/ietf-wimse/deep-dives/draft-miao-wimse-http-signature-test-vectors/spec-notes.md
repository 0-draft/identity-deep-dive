## Key Changes

This is revision -00, so there is no earlier revision and no diff. What it contains:

- Conventions (Section 2): T0 = 1795000000, verification at T0+60 by default, `expires` = `created`+300; literal signatures for the positives and N-15, and for the other mutated negatives a signature either regenerated by the runner or carried over from the base vector, as each entry states; expected outcomes stated as accept, HTTP 400 with `wimse-signature-invalid`, client rejection, or a conformance judgment; the judged set is 29 entries, and O- entries are not judged.
- Test material (Section 3): Ed25519 keys for issuer, svcA, svcB and a decoy signer "other", a P-256 key for svcC, all derived from public seeds; WIT-A, WIT-B and WIT-C with `iat` T0-60 and `exp` T0+3600; svcB trusts four `wimse-aud` values.
- Positives (Section 4): P-01 signed GET with `wimse-sign-response`; P-02 signed 404 response to P-01; P-03 ES256 POST with body and Content-Digest; P-04 CONNECT covering `@method` and `@authority`; P-05 empty query (`@query` is `?`); P-06 two signatures, the WIMSE one chosen by tag.

Checked against the base text (-08 and -09, 26 November 2026): every quoted requirement is in the section the vector names. N-05 condenses a bulleted list, and N-17 paraphrases "NOT RECOMMENDED" for 401. In -09 all quotes still hold except N-20's "Section 5.1.4 of [workload-creds]", which -09 changes to Section 5.1.3 (issue #422); workload-creds-03 has no Section 5.1.4.

Text in -00 that does not match what the vectors do:

- N-04 says the mutation "also invalidates the signature". The signature covers the Content-Digest header, not the body, and the header is unchanged, so the signature still verifies and only the recomputed digest fails (Section 5.4).
- Section 2 says the WIT placeholder is "retained verbatim in the signed material", but the P-01 Signature value is computed over the full WIT-A text (hands-on log). The printed placeholder `[WIT-A，§2 全文]` also differs from the form Section 2 describes.
- P-04's `@authority` value `svcb.example.com` follows RFC 9421 Section 2.2.3 and the -09 wording; -08, the cited base, says "the host and port of the CONNECT target".
- N-15 is meant to test the "algorithm not acceptable" rule of base Section 3.1. A verifier that takes the key from `cnf.jwk` sees an ES256 signature that fails under an Ed25519 key, so the vector is rejected as an invalid signature before that rule applies (this repository's run of the set, draft-ietf-wimse-http-signature deep dive).
- Section 1 points to the Change Log as Appendix A; it is Appendix B.

## Impact Analysis

- Upstream: Built on the text of draft-ietf-wimse-http-signature-08 and on RFC 9421 for base construction. The base moved to -09 two days after this draft; the quoted requirements survive, and -09 answers O-2 and the P-04 question. WIT validation depends on draft-ietf-wimse-workload-creds, cited without a revision.
- Downstream: Any implementation of the profile can run P-01 to P-06 and the message negatives as fixtures. The base lists Cofide and wimsey as implementations (-08 Section 4); cred-ninja reports 28 of the issue #419 vectors passing (cred-ninja/sdk PR #136). The six behavior vectors need a harness around a running sender, server or verifier, and N-20 also needs inspection or instrumentation.
- Compatibility: The expected rejections include the `wimse-signature-invalid` problem type, but base Section 3.6 makes the problem details body a SHOULD, so a server that returns a bare 400 conforms to the base and still fails a strict reading of the vectors. A verifier that enforces only the rules written for recipients can accept N-01, N-02, N-06, N-07 and N-21, whose signatures are valid. An implementation that follows -08 literally for CONNECT `@authority` fails P-04.
