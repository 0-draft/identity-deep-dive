# Context

## きっかけ

`subject.json` では、ietf-wimse トラックの「Review related draft: draft-asor-wimse-agent-delegation-chain-03」として挙げられている。ai_note は、委任元に束縛されたチェーンのドラフトがこのドラフトの Delegation Token 形式を拡張し、その束縛をこの形式に含めるべきかを問うている、と述べている。`subject.json` に Datatracker の状態はなく、メーリングリストの資料も用意されていなかった。

## なぜ重要か

このドラフトは、エージェントシステムにおける 1 つの問いを対象としている。あるエージェントが別のエージェントに作業を渡すとき、最終的にツール呼び出しを受け付けるコンポーネントは、認可サーバーを呼び出さずに、どのホップも直前のホップの権限を超えていないことをどう知るのか。ドラフトは、親ハッシュで連結した署名付きトークン、スコープと制約に対する包含関係、8 段階のオフライン検証アルゴリズムで答えている（Section 4.3、5、6）。リビジョン 03 が重要なのは、限界をより多く明記したからである。Principal の資格はチェーンでは確立されない（Section 6.1、Table 1）。ルート鍵の出所はバインディングの隙間と記録の隙間に分けられた（Section 6.4）。集計予算にはトークン外の仕組みが必要である（Section 9.4）。また、クレーム登録については競合するドラフトに譲りつつ、"del_max_depth" の実質的な意味の違いを記している（Section 10）。

## 未解決の問い

- ai_note が問うように、チェーンの委任元への束縛はこのトークン形式に属するのか。ドラフトはすでに全ホップで "sub" と "client_id" を運んでいる（Section 3.1）。用意された資料には、もう一方のドラフトは含まれていない。
- 各クレーム名の登録を 1 つにするために、draft-niyikiza-oauth-attenuating-agent-tokens との "del_max_depth" の差異はどう解消されるのか（Section 10）。
- スコープの語彙、トラストアンカーの出所、Principal の資格の確認を誰が定義するのか。ドラフトはそれぞれをワーキンググループまたは配備環境に委ねている（Section 4.5、6.4、6.1）。
- -03 は提案された規則を記録しているだけだが、複数型の認可詳細はどのように機能するのか（Section 4.4）。
