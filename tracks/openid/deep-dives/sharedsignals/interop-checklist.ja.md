- [ ] プロファイルが（#368 以降）`RS256` を固定しなくなったので、Receiver がどの署名アルゴリズムを受け入れるかを確認し、設定した許可リストにないアルゴリズムを拒否することを確認する。
- [ ] プロファイルに従う Transmitter が今も `jwks_uri` で現在の署名鍵を公開し、Receiver がそこから鍵を取得することを確認する（プロファイルの 2.3.3 節と 2.4.2 節）。
- [ ] どの SET も `typ` が `secevent+jwt` で、`sub` と `exp` のクレームを持たず、`iss` がストリーム設定と一致することを確認する（SSF 1.0 の 4.1.1、4.1.2、4.1.6、4.1.7 節）。
- [ ] プロファイルに従う Transmitter が送る SET の `events` クレームに、イベントがちょうど一つだけ入っていることを確認する（プロファイルの 2.7.1 節）。
- [ ] 提案（#355、オープン）: 記載どおりにマージされた場合、サポートされた `set_signing_alg`、指定なし、未サポートの値でストリームを作り、`400` の応答と Transmitter が返す `alg` を確認する。
- [ ] 提案（#366、オープン）: 記載どおりにマージされた場合、`email` と `iss_sub` で組んだ複合サブジェクトを送り、プロファイルに従う Receiver が受け入れることを確認する。
- [ ] 提案（#369、オープン）: 記載どおりにマージされた場合、OPTIONAL のストリーム設定プロパティに JSON `null` を送り、相手が省略と同じに扱うことを確認する。

- [ ] 提案（#363、オープン）: 記載どおりにマージされた場合、`1_0` と `1_0-ID1` の両方の Receiver に対応する Transmitter が `/.well-known/ssf-configuration` と `/.well-known/sse-configuration` を分けて公開し、それぞれ正しい `spec_version` を持つことを確認する。
